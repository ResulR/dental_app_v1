# Édition et renvoi des corrections — 17 octobre 2026

CDC §§5.1–5.2 : édition clinique En attente/Correction demandée ; édition laboratoire Acceptée avec permission orders.edit_instructions et motif obligatoire. Une demande pendante interdit toute édition ; fabrication interdit toute réécriture. Le laboratoire modifie directement : aucun nouveau circuit de proposition laboratoire n’est inventé. La demande clinique de modification Acceptée reste un lot séparé (10.5).

POST /api/v1/orders/edit-context fournit la version sélectionnée, les libellés historiques et un historique paginé. POST /api/v1/orders/edit accepte save ou resubmit_correction. Origine, session et permissions courantes sont revalidées ; la clinique reste limitée à ses propres commandes approuvées. Le client albanais appelle réellement ces routes et n’annonce jamais de succès incertain.

Save ajoute une version et ses dents sans écraser les anciennes. Une référence inchangée conserve son snapshot historique ; une référence remplacée reçoit un nouveau snapshot. Numérotation de version sous verrou de commande, compte tenu des propositions éventuelles. Le CAS version/révision empêche un second enregistrement concurrent ; le statut reste inchangé. Resubmit revalide le catalogue et les blocages, puis retourne explicitement Correction demandée vers En attente ; une nouvelle décision manuelle du laboratoire est nécessaire. L’interface impose d’enregistrer les changements avant ce renvoi.

Catalogue verrouillé avant la commande ; version, dents, commande, historique de statut si nécessaire, événement outbox, dispatch et audit appartiennent à la même transaction. Aucun e-mail envoyé. Les conflits exigent relecture ; aucun retry automatique ni affirmation de reçu idempotent pour une édition.

DENTAL_LAB_ORDER_EDIT_ENABLED reste désactivé par défaut et dépend du cycle de vie. Les privilèges sont vérifiés avant composition. Aucune configuration ni migration appliquée. Toute version contenant des fichiers, ou toute demande d’ajout de fichier, est bloquée explicitement : leur copie/revalidation sécurisée dépend du pipeline réel encore indisponible. Une ancienne référence supprimée reste lisible mais doit être remplacée ou, pour le type facultatif, retirée explicitement avant enregistrement.

Vérifications réellement réussies : 9 tests unitaires et 1 HTTP ciblé (permissions, statuts, motif, versions, demandes pendantes, resoumission, fichiers, catalogue, retouches, concurrence sérialisée et rollback par injection), builds contrats/API/web, types web, lint, architecture 197 sources et snapshot additif 5 schémas. Les doubles SQL ne prouvent ni contraintes ni isolation PostgreSQL réelles. Recette PostgreSQL et navigateur différées ; notifications internes/e-mail à finaliser via les consommateurs d’outbox. Les preuves et scripts historiques restent inchangés.
